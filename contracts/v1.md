# Device API v1: resource shapes

Base URL on the current macOS device: `http://127.0.0.1:8765/api/v1`. JSON is UTF-8. IDs are UUIDs, times are UTC ISO-8601, offsets are integer milliseconds. This file is the cross-client contract; implemented and planned fields are distinguished below.

## Implemented in #11–#15 and #29 / versioned in #21

- `GET /health` → `{status, mode, version, api_version}`.
- `GET /conversations` → active array of `{id, title, duration_ms, created_at, trashed_at, category_ids}`. `GET /conversations/{id}` and import results include `category_ids`.
- `GET /search?q=…&category_id=…` searches current active conversation titles, passage text, speaker names, and local Person names on the device, optionally within a category ID or `uncategorized`. It returns `{query, total, limited, results}` with up to 150 `{kind, conversation_id, conversation_title, revision, segment_id, start_ms, speaker, speaker_uncertain, person_id?, excerpt}` hits. A `person` hit has no conversation ID and opens its profile. Query length is 2–120 characters; a new request reflects current edits, labels, transcript generations, categories, and Trash state.
- `GET/POST /categories`, `PATCH/DELETE /categories/{id}` manage local user-defined categories. `PUT/DELETE /conversations/{id}/categories/{category_id}` assign or remove one category. Removing a category leaves conversations intact.
- `GET/POST /persons`, `GET/PATCH/DELETE /persons/{id}` manage local confirmed Person records. A Person ID is separate from acoustic cluster IDs and speaker display names; deletion requires no remaining confirmations. `PUT /conversations/{id}/person-links` takes `{person_id, segment_id, scope: "segment"|"cluster", expected_revision}` and confirms the selected passage or all current passages in that acoustic group. `POST /conversations/{id}/person-links/remove` takes `{segment_id, scope, expected_revision}`. Confirmed passages expose `person_id`, the Person name, and `speaker_label_source: "confirmed_person"`; provisional suggestions do not acquire a Person ID. `POST /persons/{id}/merge` takes `{source_id}` and moves confirmed links from the source Person. `POST /persons/{id}/move-conversation` takes `{conversation_id, target_id}` to separate an incorrect merged association; `DELETE /persons/{id}/conversations/{conversation_id}` removes one conversation's links. Profiles return active conversation links with representative source segment IDs and timestamps; older generation links fall back to the timestamp on navigation.
- `POST /conversations/{id}/trash` moves a conversation to Recently Deleted and hides it from active library, search, audio, and conversation routes without removing its data. `GET /trash` lists these items with `trashed_at` and `expires_at`; `POST /trash/{id}/restore` restores one and clears the retention clock. Items expire 30 days after their latest move and are deleted by a device startup/hourly sweep once jobs settle. `DELETE /trash/{id}` permanently removes private media and dependent records after queued or running speech/AI jobs settle; otherwise it returns HTTP 409. The browser requires a separate typed confirmation for manual permanent deletion.
- `POST /conversations/import` multipart `file` → `{conversation, duplicate}`.
- `GET /conversations/{id}` → conversation summary.
- `GET /conversations/{id}/audio` → original media with byte-range support and `Cache-Control: no-store`.
- Errors: HTTP 400 for invalid media, 404 for unknown ID. A future error envelope will add stable codes before more clients depend on it.
- `GET /capabilities` reports installed English ASR and speaker models and current readiness.
- `POST /conversations/{id}/processing-jobs` starts or returns a durable idempotent job. `GET /conversations/{id}/processing-job` finds it after reload. `GET /jobs/{id}` polls state, stage, progress, error, and aggregate metrics.
- If a fresh ASR pass changes passage IDs that carry user overlays, the job succeeds with stage `review ready` and leaves the source generation active. `GET /conversations/{id}/transcript/review` returns `{source_version, target_version, source_revision, state, items, decisions}`; each item includes source wording/time, overlay kind/value, and nearby target candidates with text/time match scores. `PUT /conversations/{id}/transcript/review/decisions` takes `{item_id, target_segment_id?}`; null explicitly keeps an item unresolved. `POST /conversations/{id}/transcript/review/activate` requires every item to have a decision and atomically activates only explicitly mapped overlays. `POST /conversations/{id}/transcript/review/keep-source` keeps the current generation. `GET /conversations/{id}/transcript/review/history` returns durable decision snapshots. All review evidence stays on the device.
- `GET /conversations/{id}/transcript` returns `{conversation_id, revision, generation_version, language, segments, turns, speaker_labels, highlights}` after success. Segments carry offsets, displayed text, `original_text` when edited, a provisional acoustic speaker cluster, uncertainty, and text/speaker provenance. When the versioned on-device ASR output reproduces the text exactly, `words` contains `{text, start_offset, end_offset, start_ms, end_ms, confidence, provenance}` measured from native Whisper tokens. Edited passages expose no word spans until re-aligned.
- `GET /conversations/{id}/transcript/generations` lists retained machine generations; `GET /conversations/{id}/transcript/generations/{version}` returns one unedited machine output.
- `PATCH /conversations/{id}/transcript/segments` takes `{edits: [{segment_id, text}], expected_revision}` for a transcript-wide edit session. The service validates all IDs and the revision before atomically saving passage overlays in one revision; a 409 leaves browser wording pending for recovery.
- `PATCH /conversations/{id}/transcript/segments/{segment_id}` takes `{text, expected_revision}` and returns `{revision}`. HTTP 409 means the caller must reload before retrying.
- `PUT /conversations/{id}/speakers/label` takes `{scope: "cluster"|"segment", target_id, name, expected_revision}`. `name: null` clears that manual label.
- `GET /vocabulary?kind=name|other` lists global speech hints with `{id, term, kind, created_at, updated_at}`; omit `kind` for both sections. `POST /vocabulary` adds one term, defaulting to `other`, and `PATCH/DELETE /vocabulary/{term_id}` edit or remove one. `POST /vocabulary/batch` takes `{terms, kind}` and returns `{added, skipped}`; matching terms are skipped by case-insensitive identity. `POST /vocabulary/move` takes `{ids, kind}` and `POST /vocabulary/delete` takes `{ids}`; each selected operation is atomic. Existing terms migrate to `other`. A new processing job snapshots the newest terms from both sections that fit its 400-character Whisper prompt; editing vocabulary does not rewrite prior output.
- `POST /conversations/{id}/highlights` takes `{segment_id, start_offset, end_offset, expected_revision}` with character offsets in the displayed text and returns an anchored quote. `DELETE /conversations/{id}/highlights/{highlight_id}` removes it. The transcript response includes all saved highlights.
- `GET /recordings` lists unfinished browser capture sessions and durable chunk counts. `POST /recordings` creates one with `{title, media_type}`. `PUT /recordings/{id}/chunks/{sequence}` stores bounded raw encoder chunks idempotently. `POST /recordings/{id}/events` records pause/resume/device-ended events and media position. `POST /recordings/{id}/finalize` verifies and remuxes saved chunks, then returns `{conversation, duplicate}`. `DELETE /recordings/{id}` explicitly discards an unfinished session.
- `POST /conversations/{id}/ai-runs` takes `{kind: "summary"|"answer", question?, force?}` and explicitly sends bounded displayed transcript excerpts to Nebius. `force: true` is valid only for a summary and starts a new run for the current revision after success; it reuses an active summary run. Ordinary requests remain idempotent. `GET /conversations/{id}/ai-runs` lists runs; `GET /ai-runs/{run_id}` polls one. A run includes state, stage, source revision, model ID, prompt version, provider request IDs, aggregate token usage, errors, and a `stale` flag. Successful summaries contain source-linked overview, topics, decisions, and action proposals. Successful answers contain text, source segment IDs, and an insufficient-evidence flag. A transcript edit makes older results stale; it does not rewrite them.
- `POST /conversations/{id}/clean-runs` starts or retries a versioned Nemotron cleanup for the displayed transcript revision. `GET /conversations/{id}/clean-runs` lists runs and `GET /clean-runs/{run_id}` polls one. Successful results contain one cleaned passage per source segment, with original text, stable ID, timestamps, speaker, and review flag. `PATCH /clean-runs/{run_id}/segments` takes `{edits: [{segment_id, text}], expected_revision}` and saves a transcript-wide edit session atomically. `PUT /clean-runs/{run_id}/segments/{segment_id}/review` takes `{expected_revision}` and records an audio-review confirmation. Both return `{edit_revision}`; HTTP 409 preserves browser wording for retry. The single-passage `PATCH /clean-runs/{run_id}/segments/{segment_id}` remains available. The browser shows the Edited Transcript tab after success and clicking a passage seeks audio.
- `POST /conversations/{id}/speaker-rematch` queues or returns a persisted on-device acoustic rematch job. `GET /jobs/{job_id}` polls it with `kind: "rematch"`, stage, state, and aggregate metrics. The resulting transcript generation keeps segment IDs and text, adds match source, score, margin, original acoustic cluster, and unresolved state, and preserves user overlays. A repeated request for the same source generation and algorithm version returns the same job.
- `POST /conversations/{id}/word-alignment` optionally takes `{source_generation_version}` and queues an idempotent on-device job for that retained generation. `GET /jobs/{job_id}` polls it with `kind: "word_alignment"`. The resulting generation keeps the source passage IDs, text, speakers, and times; it adds only word spans matched by text and nearby measured audio time. Metrics include `word_count` and `word_coverage`. Existing manual overlays remain attached to the same IDs.

## To implement in follow-ups

- `GET /capabilities` will also report recording, summary, device identity, and additional languages as adapters become available.
- Processing jobs will add input digest and model digests to their public contract. A client polls initially; event streaming can be added without changing the resource.
- A future alignment adapter may improve word offsets or re-align user-edited wording without retranscribing. Source word spans are never synthesized by splitting segment offsets evenly.

## Local login (#16, #68)

`stellis serve` sets `STELLIS_AUTH_MODE=required` by default; explicit `STELLIS_AUTH_MODE=open` keeps an open loopback development workspace. Required mode gates all workspace pages and `/api` resources except health and `/api/v1/auth/*`. The static browser assets and `/auth` page remain public. `GET /api/v1/auth/status` reports whether registration is open and the current username. `POST /api/v1/auth/register` creates the only normal account and signs it in; `POST /api/v1/auth/login` starts a seven-day session; `POST /api/v1/auth/logout` revokes it. Both credential requests take `{username, password}`. The normal signup password minimum is 12 characters. Sessions use an HttpOnly, SameSite Strict cookie; protected API calls without one return 401, and protected pages redirect to `/auth`. Cross-origin mutating requests are rejected. There is no local password reset. When both `STELLIS_DEV_ACCOUNT=1` and `STELLIS_DEV_PASSWORD` are set, username `dev` can sign in with that password without registration or the normal password minimum. This is limited to the loopback development service and shares its data directory. This local mode has no multi-user ownership or remote authorization; those remain #16.

## Notebooks, capture time, and account settings

`GET /api/v1/conversations` rows include `recorded_at` (UTC capture time or `null`), `notebook_id` (or `null`), and `summary_line` (the first overview point of the newest successful Summary, after user edits, or `null`). The list sorts by `recorded_at`, falling back to `created_at`, newest first. `POST /api/v1/conversations/import` accepts optional form fields `recorded_at` (ISO 8601 with an offset; values before 1990 or more than five minutes ahead are ignored) and `notebook_id`. `POST /api/v1/recordings` accepts an optional `notebook_id`; finalization stores the session start as `recorded_at` and places the conversation in that notebook.

`GET /api/v1/notebooks` returns `{palette, notebooks}`. Each notebook has `id`, `name`, `color` (one of the five palette values), `created_at`, `conversations` newest first, and `progress`: up to three decisions and action proposals, or topics when there are none, from the newest conversation's Summary. Notebooks sort by their newest conversation, or by creation when empty. `POST /api/v1/notebooks` takes `{name, color?}`; names are unique ignoring case. `PATCH /api/v1/notebooks/{id}` takes `{name?, color?}`. `DELETE /api/v1/notebooks/{id}` keeps its conversations without a notebook. `PUT /api/v1/conversations/{id}/notebook` takes `{notebook_id}` or `null`.

`GET /api/v1/account` returns `{username, name, email}`. `PATCH /api/v1/account` takes `{name, email}`. `POST /api/v1/account/username` takes `{username, password}`. `POST /api/v1/account/password` takes `{current_password, new_password}` and signs out every other session. `DELETE /api/v1/account` takes `{password, confirm: "DELETE"}`; it refuses with 409 while processing runs, then removes every conversation through permanent deletion, unfinished captures, vocabulary, people, notebooks, categories, calendar tokens, and the account, and clears the session cookie. Default categories return for the next account. These routes return 404 in open mode and 403 for the shared dev login. `GET /api/v1/calendar/{provider}/authorize` accepts `return_to` of `/` or `/settings` for the page the callback returns to.

## Collections

A collection is an optional, non-nesting group of notebooks; a notebook belongs to at most one. [ADR 0058](../docs/decisions/0058-pages-collections-markdown-dialect.md) records the decision.

`GET /api/v1/collections` returns `{palette, collections}`. Each collection has `id`, `name`, `color` (one of the notebook palette values), `created_at`, and `notebook_ids` in notebook creation order. `POST /api/v1/collections` takes `{name, color?}` and returns 201 with the new collection; the default color follows palette order. `PATCH /api/v1/collections/{id}` takes `{name?, color?}`. `DELETE /api/v1/collections/{id}` keeps its notebooks without a collection. `PUT /api/v1/notebooks/{id}/collection` takes `{collection_id}` or `null` and returns `{id, collection_id}`. Each notebook in `GET /api/v1/notebooks` carries `collection_id` (or `null`).

Names follow the notebook rules (1 to 80 characters after whitespace is collapsed, unique ignoring case). A duplicate name returns 409, an invalid name or color returns 400, and an unknown collection or notebook returns 404. Account deletion removes every collection.

## Pages (#248)

A page is a title and revisioned Markdown with no audio, stored in `pages` ([ADR 0058](../docs/decisions/0058-pages-collections-markdown-dialect.md)). Titles are 1 to 200 characters after whitespace is collapsed; an empty or missing title is stored as `Untitled`. A page belongs to at most one notebook.

`GET /api/v1/pages?notebook_id=` lists active pages as `{id, title, notebook_id, created_at, updated_at}`, newest `updated_at` first; `notebook_id` is a notebook ID, `none` for pages without a notebook, or omitted for all. `POST /api/v1/pages` takes `{title?, notebook_id?, markdown?}` and returns 201 with the page. `GET /api/v1/pages/{id}` returns `{id, title, markdown, revision, notebook_id, created_at, updated_at}`. `PATCH /api/v1/pages/{id}` takes `{title}`. `PUT /api/v1/pages/{id}/markdown` takes `{markdown, expected_revision}`, returns the page with the revision increased by one, returns 409 for a stale revision, and returns 413 when the body exceeds 200,000 UTF-8 bytes. `PUT /api/v1/pages/{id}/notebook` takes `{notebook_id}` or `null`; an unknown notebook returns 404. An unknown or trashed page returns 404, and an invalid title returns 400.

`POST /api/v1/pages/{id}/trash` moves a page to Recently Deleted. `GET /api/v1/trash` lists conversations and pages together; every item has `kind` of `conversation` or `page`, and conversation fields are unchanged. Page items carry `id`, `title`, `notebook_id`, `created_at`, `updated_at`, `trashed_at`, `expires_at`, and an empty `category_ids`. `POST /api/v1/trash/{id}/restore` and `DELETE /api/v1/trash/{id}` look the ID up among conversations, then among pages. Pages trashed more than 30 days are removed by the expiry sweep, and account deletion removes every page.

Each notebook in `GET /api/v1/notebooks` has `pages`: `[{id, title, updated_at}]` for its active pages, newest first. `DELETE /api/v1/notebooks/{id}` leaves its pages active with `notebook_id` `null`.

## To-dos (#255)

A to-do is a Markdown task line in conversation notes or a page ([ADR 0059](../docs/decisions/0059-todos-as-task-lines-and-suggestions.md)). A line matches `- [ ] text`, with `-`, `*`, or `+` as the bullet and any indent. The marker `[ ]` is `open`, `[x]` or `[X]` is `done`, and `[-]` is `canceled`. A trailing ` ^t` plus six characters from `0-9a-z` is the line's ID. Lines inside fenced code blocks are not tasks. Line numbers are 1-based.

Every save that stores notes or a page (`PUT /api/v1/conversations/{id}/notes`, `PUT /api/v1/pages/{id}/markdown`, `POST /api/v1/pages`, and moving capture notes into a conversation) indexes the task lines into `todo_items` in the same transaction. Recording notes before they belong to a conversation are not indexed. A task line without an ID takes the ID of an unused item from the same source with the same text, ignoring case and extra whitespace. Otherwise it gets a new random ID. An ID that another source already owns, or that repeats earlier in the document, is replaced. The stored Markdown and the `markdown` field of the response include the IDs. The revision check is unchanged. Items whose lines are gone are deleted.

Each item records `created_at` when first indexed, `completed_at` when its status becomes `done`, and `canceled_at` when it becomes `canceled`. Each is cleared when the status leaves that value.

`PUT .../notes` and `PUT .../markdown` accept an optional `todo_dates`: `{<line id>: {due_date: "YYYY-MM-DD", due_time: "HH:MM" | null} | null}`. A known ID gets the date and time, and `null` clears them. An unknown ID is ignored. The server checks the shape only and parses no natural-language date.

`GET /api/v1/todos?notebook_id=&status=` takes `notebook_id` as a notebook ID, `none`, or `all` (default), and `status` as `open` (default), `done`, or `canceled`. It returns `{groups: [{source: {kind, id, title, notebook_id}, items: [{id, text, status, due_date, due_time, created_at, completed_at, canceled_at}]}]}`. `kind` is `conversation` or `page`. Groups are ordered by the source's recording or creation time, newest first, and items by line. Trashed conversations and pages are left out.

`PATCH /api/v1/todos/{id}` takes `{status}` and returns the item. It rewrites that line's marker in the source Markdown, increases the source's revision by one, and reindexes, all in one `BEGIN IMMEDIATE` transaction. An editor holding the earlier revision receives 409 on its next save. An unknown ID or a trashed source returns 404, and an invalid status returns 422.

Permanently deleting a conversation or page, including the 30-day expiry sweep, removes its items. Account deletion clears `todo_items`.

## Suggestions (#256)

Agents add or close to-dos only through suggestions that the user reviews ([ADR 0059](../docs/decisions/0059-todos-as-task-lines-and-suggestions.md)). A suggestion never edits a document until it is accepted. Agents and chat are not part of this contract.

**To-do list setting.** `collections.todo_list` is `on` or `off` (default `off`). `notebooks.todo_list` is `inherit` (default), `on`, or `off`. `PATCH /api/v1/collections/{id}` and `PATCH /api/v1/notebooks/{id}` accept `todo_list`, and an invalid value returns 422. A notebook's own `on` or `off` decides. `inherit` follows its collection, and a notebook without a collection counts as `off`. Each notebook in `GET /api/v1/notebooks` has `todo_list` and `todo_enabled` (the resolved boolean). Collections in `GET /api/v1/collections` have `todo_list`.

**Suggestion.** `{id, run_id, author, target_kind, target_id, operation, todo_id, values, original_values, previous, source_kind, source_id, evidence, state, created_at, amended_at, decided_at}`.
- `author` names the agent, for example `transcript-agent`. `target_kind` is `conversation` or `page`, and `target_id` is that conversation's or page's ID.
- `operation` is `add_todo` with `values` `{text, due_date?, due_time?}`, or `set_todo_status` with `values` `{status}`, `todo_id` set, and `previous` `{status}`. `previous` is the line's status when the suggestion was made. `text` is 1 to 500 characters with whitespace collapsed, `status` is `open`, `done`, or `canceled`, `due_date` is `YYYY-MM-DD`, and `due_time` is `HH:MM` and needs a `due_date`.
- `evidence` is `[{segment_id, quote}]`. `source_kind` and `source_id` name the conversation or page the agent read, and permanently deleting that source deletes the suggestion.
- `state` is `pending`, `accepted`, `rejected`, or `superseded`. `original_values` is `null` until the user amends the suggestion, and then holds the agent's first version.

**Proposing.** The device service creates suggestions through `suggestions.propose`, which has no HTTP route. It validates the values. An `add_todo` raises `PermissionError` unless the target's notebook has `todo_enabled`. A `set_todo_status` raises `LookupError` unless `todo_id` is an existing to-do of that target. A trashed or unknown target raises `LookupError`.

`GET /api/v1/suggestions?target_kind=&target_id=` and `GET /api/v1/suggestions?notebook_id=` return `{suggestions: [...]}` with the pending suggestions in creation order, each with its evidence. The notebook form covers the notebook's active conversations and pages. Any other combination of parameters returns 400, and an unknown notebook returns 404. Each item in `GET /api/v1/todos` has `pending_suggestions`, the IDs of pending suggestions whose `todo_id` is that item.

`PATCH /api/v1/suggestions/{id}` takes `{values}`, validates them as above, and replaces the values of a pending suggestion. The first amendment copies the agent's values to `original_values`. Each amendment sets `amended_at`. A suggestion that is not pending returns 409, an invalid value 400, and an unknown ID 404.

**Bulk calls.** `POST /api/v1/suggestions/accept`, `/reject`, and `/preview` take `{ids}`, and preview also takes `decision`: `accept` or `reject`. An unknown ID in any of them returns 404 and changes nothing. Suggestions that are not pending are skipped.

- `accept` groups the pending suggestions by target and applies each group in creation order in one `BEGIN IMMEDIATE` transaction. If a group applies at least one change, the target's revision goes up by one and its task lines are reindexed in that transaction. An editor holding the earlier revision receives 409 on its next save. It returns `{accepted: [ids], superseded: [ids]}`.
- `add_todo` appends `- [ ] <text> ^<new id>` after the last non-blank line of the section headed exactly `## To-dos` (level 2), which ends at the next level 1 or 2 heading. If the document has no such section, a blank line, the heading, a blank line, and the item are added at the end. A conversation without notes gets notes at revision 1. The due date and time are stored on the new item. The suggestion's `todo_id` becomes the new ID.
- `set_todo_status` rewrites the line's marker only when the line's current status equals `previous`. Otherwise the suggestion becomes `superseded`. A target that is trashed or deleted supersedes all its suggestions.
- `reject` sets `rejected` and returns `{rejected: [ids]}`.
- `preview` returns `{targets: [{target_kind, target_id, markdown}]}`, one entry per target, with the stored form of the document (task IDs included) as it would be after the decision. It runs the accept transaction and rolls it back, so nothing is saved. A `reject` decision returns each document unchanged.

**The user's edits win.** Any save that reindexes a source supersedes pending suggestions: a changed status supersedes the pending `set_todo_status` suggestions on that line, and a removed line supersedes all pending suggestions on it. Permanently deleting a conversation or page, including the 30-day sweep, deletes the suggestions that target it or cite it as a source. Account deletion clears `suggestions`.

## Link previews (#250)

`POST /api/v1/link-previews` takes `{url}` and returns `{url, final_url, title, description, site_name, image_url, icon_url, status}`, where `status` is `ok` or `failed` and absent fields are `null`. `url` is the request URL with its fragment removed. A malformed URL or one that is not http or https returns 422. The device service serves a stored row that is newer than 7 days (`ok`) or 1 day (`failed`) and otherwise fetches the page, with an 8-second timeout, a `User-Agent` of `Stellis link preview`, at most 5 redirects followed one at a time, and at most 1 MB of body read. Before each request, including each redirect, the host is resolved and the request is refused with 400 `This address can't be previewed` when any address is private, loopback, link-local, multicast, reserved, or unspecified; a refusal is not stored. Only `text/html` is parsed. Any other content type is stored `ok` with `final_url` as the only data. A network error, an HTTP error status, or too many redirects is stored `failed` and returned with 200. The title comes from `og:title`, `twitter:title`, then `<title>` (300 characters at most); the description from `og:description`, `twitter:description`, then `meta[name=description]` (600 characters at most); the image from `og:image` then `twitter:image`; the site name from `og:site_name`; the icon from the first `link` of rel `icon`, `shortcut icon`, or `apple-touch-icon`, else `/favicon.ico`. Relative URLs resolve against the final URL. Image bytes are not stored; the browser loads `image_url` directly. [ADR 0058](../docs/decisions/0058-pages-collections-markdown-dialect.md) records the decision.

## Local calendars (#183, #184)

The device API exposes `GET /api/v1/calendar/connections`, `GET /api/v1/calendar/{google|microsoft}/authorize`, `GET /api/v1/calendar/{google|microsoft}/callback`, `POST /api/v1/calendar/{google|microsoft}/disconnect`, and `GET /api/v1/calendar/meetings`. The authorize response contains a provider URL for an authorization-code/PKCE redirect; the callback consumes a ten-minute single-use state. Local sign-in gates the workspace endpoints. The callback uses its state to complete the provider exchange and returns to the originating loopback address.

Only the Google primary or Microsoft default calendar is read. Meetings are a bounded, normalized 14-day view (`id`, `provider`, `title`, UTC `start`/`end` for timed events, source dates for all-day events, `all_day`), with at most 100 results. The device stores OAuth tokens in a private, mode-`0600` SQLite file and no event list. Disconnect removes local tokens. No token or calendar detail is sent to the sync service or Nebius. A browser Record action copies the event title into the existing local recording flow; it does not create an event or start a meeting bot. Each meeting also carries `has_notes`. `GET /api/v1/calendar/notes?provider=…&event_id=…` returns `{markdown, revision, updated_at}` for notes written before a meeting, and `PUT /api/v1/calendar/notes` takes `{provider, event_id, markdown, expected_revision}`, returning 409 for a stale revision. `POST /api/v1/recordings` accepts optional `calendar_provider` and `calendar_event_id`; the event's notes become the new session's My Notes. [ADR 0057](../docs/decisions/0057-notes-before-a-meeting.md) records the storage choice. [ADR 0050](../docs/decisions/0050-local-read-only-calendars.md) records the privacy boundary and limits.

## Hosted sync (separate origin and service, #17)

The separate loopback development identity service (#71) implements `GET /sync/v1/health`, `POST /sync/v1/auth/register|login|logout`, `GET /sync/v1/me`, `POST /sync/v1/sessions/revoke-all`, and `GET/POST /sync/v1/devices` plus `DELETE /sync/v1/devices/{device_id}`. Registration and login take `{username, password}` and set an HttpOnly, SameSite Strict, seven-day session cookie. Device registration takes `{name}`; device IDs are random and each list, create, and revoke operation is scoped to the signed-in account. The service binds to loopback only and its password accounts are development identity, not production OIDC.

The encrypted text-journal prototype (#73) implements `GET/POST /sync/v1/vault` for one immutable, public 16-byte salt and an encrypted passphrase check per account. `POST /sync/v1/entries` takes `{id, item_id, iv, ciphertext}` with canonical random UUIDs, a 12-byte base64 IV, and at most 65,536 decoded ciphertext bytes. Reusing an entry ID with identical bytes returns its original sequence; different bytes return 409. `GET /sync/v1/entries?after=&limit=` returns only the signed-in account's append-only entries and the latest cursor, with a maximum page of 100. Browser Web Crypto derives a nonextractable AES-256-GCM key from a separate vault passphrase and public salt using PBKDF2-HMAC-SHA256; each entry uses a fresh IV and authenticates the user, item, and entry IDs as additional data. The browser queues encrypted note envelopes in IndexedDB while offline. No plaintext note, passphrase, or content key is sent to the service.

The device browser snapshot adapter (#77) exposes `GET /api/v1/sync-config` with a configured loopback `origin` or `null`. It reads a selected conversation and effective transcript from its local API, divides passages into encrypted parts of at most ten passages and 45 KB plaintext each, then sends an encrypted manifest containing title, source ID, source loopback origin, revision, passage count, and part IDs. The account browser assembles only complete manifests with ordered matching parts and shows a read-only text snapshot. Passage links use the encrypted source origin only when it is an exact loopback origin with a port; missing origins in older snapshots use the default port 8765, while invalid origins have no link. Links work only on the recording machine. The sync service sees ciphertext sizes, opaque IDs, and order; it has no plaintext conversation route.

The encrypted media extension (#17) adds `POST/GET /sync/v1/media/{media_id}/chunks/{index}` for account-owned opaque audio chunks. IDs are canonical UUIDs, indexes are 0–511, IVs are 12 bytes, decoded ciphertext is at most 256 KiB plus the AES-GCM tag, identical retries succeed, and conflicting retries return 409. The device browser streams local audio into 256 KiB chunks, encrypts each with AES-256-GCM under the vault key using account ID, media ID, and chunk index as authenticated data, and uploads all chunks before the encrypted conversation manifest. The manifest adds media ID, count, type, and byte length. The account browser decrypts and authenticates every chunk before creating a local audio player. The service stores ciphertext only, capped at 192 MiB of encoded chunks per account. This is a one-way media copy, not edit convergence, deletion propagation, offline retry, or cryptographic device revocation.

For the loopback development bridge (#75), `STELLIS_DEVICE_ORIGIN` may name one exact loopback origin with a port. Credentialed CORS allows that origin to call `/sync/v1`; it is disabled by default. A foreign Origin fails preflight or mutating requests. The caller must use `credentials: 'include'` after a login on the account origin. This validates the browser connection only; a production cross-site identity flow cannot rely on these development cookies.

Planned encrypted media chunks and full conversation operation sync will accept opaque ciphertext envelopes only. Production authentication is expected to use OIDC session/device membership (#16). Hosted sync must never implement device-service audio or transcript endpoints. Browser key enrollment/decryption stays client-side (#17).
