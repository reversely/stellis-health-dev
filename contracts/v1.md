# Device API v1: resource shapes

Base URL on the current macOS device: `http://127.0.0.1:8765/api/v1`. JSON is UTF-8. IDs are UUIDs, times are UTC ISO-8601, offsets are integer milliseconds. This file is the cross-client contract; implemented and planned fields are distinguished below.

## Implemented in #11–#15 and #29 / versioned in #21

- `GET /health` → `{status, mode, version, api_version}`.
- `GET /conversations` → active array of `{id, title, duration_ms, created_at, trashed_at, category_ids}`. `GET /conversations/{id}` and import results include `category_ids`.
- `GET /search?q=…&category_id=…` searches current active conversation titles, passage text, speaker names, and local Person names on the device, optionally within a category ID or `uncategorized`. It returns `{query, total, limited, results}` with up to 150 `{kind, conversation_id, conversation_title, revision, segment_id, start_ms, speaker, speaker_uncertain, person_id?, excerpt}` hits. A `person` hit has no conversation ID and opens its profile. Query length is 2–120 characters; a new request reflects current edits, labels, transcript generations, categories, and Trash state.
- `GET/POST /categories`, `PATCH/DELETE /categories/{id}` manage local user-defined categories. `PUT/DELETE /conversations/{id}/categories/{category_id}` assign or remove one category. Removing a category leaves conversations intact.
- `GET/POST /persons`, `GET/PATCH/DELETE /persons/{id}` manage local confirmed Person records. A Person ID is separate from acoustic cluster IDs and speaker display names; deletion requires no remaining confirmations. `PUT /conversations/{id}/person-links` takes `{person_id, segment_id, scope: "segment"|"cluster", expected_revision}` and confirms the selected passage or all current passages in that acoustic group. `POST /conversations/{id}/person-links/remove` takes `{segment_id, scope, expected_revision}`. Confirmed passages expose `person_id`, the Person name, and `speaker_label_source: "confirmed_person"`; provisional suggestions do not acquire a Person ID. `POST /persons/{id}/merge` takes `{source_id}` and moves confirmed links from the source Person. `POST /persons/{id}/move-conversation` takes `{conversation_id, target_id}` to separate an incorrect merged association; `DELETE /persons/{id}/conversations/{conversation_id}` removes one conversation's links. Profiles return active conversation links with representative source segment IDs and timestamps; older generation links fall back to the timestamp on navigation.
- `POST /conversations/{id}/trash` moves a conversation to Recently Deleted and hides it from active library, search, audio, and conversation routes without removing its data. `GET /trash` lists these items with `trashed_at` and `expires_at`; `POST /trash/{id}/restore` restores one and clears the retention clock. Items expire 30 days after their latest move and are deleted by a device startup/hourly sweep once jobs settle. `DELETE /trash/{id}` permanently removes private media and dependent records after queued or running speech/AI jobs settle; otherwise it returns HTTP 409. The browser requires a separate typed confirmation for manual permanent deletion.
- `POST /conversations/import` multipart `file` → `{conversation, duplicate}`.
- `GET /conversations/{id}` → conversation summary.
- `GET /conversations/{id}/audio` → original media with byte-range support and `Cache-Control: no-store`.
- Errors: HTTP 400 for invalid media, 404 for unknown ID. A future error envelope will add stable codes before more clients depend on it.
- `GET /capabilities` reports installed English ASR and speaker models and current readiness.
- `POST /conversations/{id}/processing-jobs` starts or returns a durable idempotent job. `GET /conversations/{id}/processing-job` finds it after reload. `GET /jobs/{id}` polls state, stage, progress, error, and aggregate metrics.
- If a fresh ASR pass changes passage IDs that carry user overlays, the job succeeds with stage `review ready` and leaves the source generation active. `GET /conversations/{id}/transcript/review` returns `{source_version, target_version, source_revision, state, items, decisions}`; each item includes source wording/time, overlay kind/value, and nearby target candidates with text/time match scores. `PUT /conversations/{id}/transcript/review/decisions` takes `{item_id, target_segment_id?}`; null explicitly keeps an item unresolved. `POST /conversations/{id}/transcript/review/activate` requires every item to have a decision and atomically activates only explicitly mapped overlays. `POST /conversations/{id}/transcript/review/keep-source` keeps the current generation. `GET /conversations/{id}/transcript/review/history` returns durable decision snapshots. All review evidence stays on the device.
- `GET /conversations/{id}/transcript` returns `{conversation_id, revision, generation_version, language, segments, turns, speaker_labels, highlights}` after success. Segments carry offsets, displayed text, `original_text` when edited, a provisional acoustic speaker cluster, uncertainty, and text/speaker provenance. When the versioned on-device ASR output reproduces the text exactly, `words` contains `{text, start_offset, end_offset, start_ms, end_ms, confidence, provenance}` measured from native Whisper tokens. Edited passages expose no word spans until re-aligned.
- `GET /conversations/{id}/transcript/generations` lists retained machine generations; `GET /conversations/{id}/transcript/generations/{version}` returns one unedited machine output.
- `PATCH /conversations/{id}/transcript/segments` takes `{edits: [{segment_id, text}], expected_revision}` for a transcript-wide edit session. The service validates all IDs and the revision before atomically saving passage overlays in one revision; a 409 leaves browser wording pending for recovery.
- `PATCH /conversations/{id}/transcript/segments/{segment_id}` takes `{text, expected_revision}` and returns `{revision}`. HTTP 409 means the caller must reload before retrying.
- `PUT /conversations/{id}/speakers/label` takes `{scope: "cluster"|"segment", target_id, name, expected_revision}`. `name: null` clears that manual label.
- `GET/POST /vocabulary`, `PATCH/DELETE /vocabulary/{term_id}` manage global speech hints. Each processing job snapshots the current list into its version; editing vocabulary does not rewrite prior output.
- `POST /conversations/{id}/highlights` takes `{segment_id, start_offset, end_offset, expected_revision}` with character offsets in the displayed text and returns an anchored quote. `DELETE /conversations/{id}/highlights/{highlight_id}` removes it. The transcript response includes all saved highlights.
- `GET /recordings` lists unfinished browser capture sessions and durable chunk counts. `POST /recordings` creates one with `{title, media_type}`. `PUT /recordings/{id}/chunks/{sequence}` stores bounded raw encoder chunks idempotently. `POST /recordings/{id}/events` records pause/resume/device-ended events and media position. `POST /recordings/{id}/finalize` verifies and remuxes saved chunks, then returns `{conversation, duplicate}`. `DELETE /recordings/{id}` explicitly discards an unfinished session.
- `POST /conversations/{id}/ai-runs` takes `{kind: "summary"|"answer", question?, force?}` and explicitly sends bounded displayed transcript excerpts to Nebius. `force: true` is valid only for a summary and starts a new run for the current revision after success; it reuses an active summary run. Ordinary requests remain idempotent. `GET /conversations/{id}/ai-runs` lists runs; `GET /ai-runs/{run_id}` polls one. A run includes state, stage, source revision, model ID, prompt version, provider request IDs, aggregate token usage, errors, and a `stale` flag. Successful summaries contain source-linked overview, topics, decisions, and action proposals. Successful answers contain text, source segment IDs, and an insufficient-evidence flag. A transcript edit makes older results stale; it does not rewrite them.
- `POST /conversations/{id}/clean-runs` starts or retries a versioned Nemotron cleanup for the displayed transcript revision. `GET /conversations/{id}/clean-runs` lists runs and `GET /clean-runs/{run_id}` polls one. Successful results contain one cleaned passage per source segment, with original text, stable ID, timestamps, speaker, and review flag. `PATCH /clean-runs/{run_id}/segments` takes `{edits: [{segment_id, text}], expected_revision}` and saves a transcript-wide edit session atomically. `PUT /clean-runs/{run_id}/segments/{segment_id}/review` takes `{expected_revision}` and records an audio-review confirmation. Both return `{edit_revision}`; HTTP 409 preserves browser wording for retry. The single-passage `PATCH /clean-runs/{run_id}/segments/{segment_id}` remains available. The browser shows the Edited Transcript tab after success and clicking a passage seeks audio.
- `POST /conversations/{id}/speaker-rematch` queues or returns a persisted on-device acoustic rematch job. `GET /jobs/{job_id}` polls it with `kind: "rematch"`, stage, state, and aggregate metrics. The resulting transcript generation keeps segment IDs and text, adds match source, score, margin, original acoustic cluster, and unresolved state, and preserves user overlays. A repeated request for the same source generation and algorithm version returns the same job.
- `POST /conversations/{id}/word-alignment` optionally takes `{source_generation_version}` and queues an idempotent on-device job for that retained generation. `GET /jobs/{job_id}` polls it with `kind: "word_alignment"`. The resulting generation keeps the source passage IDs, text, speakers, and times; it adds only word spans matched by text and nearby measured audio time. Metrics include `word_count` and `word_coverage`. Existing manual overlays remain attached to the same IDs.

## To implement in follow-ups

- `GET /capabilities` will also report recording, summary, device identity, and additional languages as adapters become available.
- Processing jobs will add input digest and model digests to their public contract. A client polls initially; event streaming can be added without changing the resource.
- A future alignment adapter may improve word offsets or re-align user-edited wording without retranscribing. Source word spans are never synthesized by splitting segment offsets evenly.
- `GET/PUT /vocabulary` holds user terms and language so a new processing run can use them where the installed ASR adapter supports hints.

## Local login (opt-in development mode, #68)

`STELLIS_AUTH_MODE=required` gates all workspace pages and `/api` and `/api/v1` resources except health and `/api/v1/auth/*`. The static browser assets and `/auth` page remain public. `GET /auth/status` reports whether registration is open and the current username. `POST /auth/register` creates the only account and signs it in; `POST /auth/login` starts a seven-day session; `POST /auth/logout` revokes it. Both credential requests take `{username, password}`. Sessions use an HttpOnly, SameSite Strict cookie; protected API calls without one return 401, and protected pages redirect to `/auth`. Cross-origin mutating requests are rejected. This local mode has no multi-user ownership, remote authorization, or password recovery; those remain #16.

## Hosted sync (separate origin and service, #17)

The separate loopback development identity service (#71) implements `GET /sync/v1/health`, `POST /sync/v1/auth/register|login|logout`, `GET /sync/v1/me`, `POST /sync/v1/sessions/revoke-all`, and `GET/POST /sync/v1/devices` plus `DELETE /sync/v1/devices/{device_id}`. Registration and login take `{username, password}` and set an HttpOnly, SameSite Strict, seven-day session cookie. Device registration takes `{name}`; device IDs are random and each list, create, and revoke operation is scoped to the signed-in account. The service binds to loopback only and its password accounts are development identity, not production OIDC.

The encrypted text-journal prototype (#73) implements `GET/POST /sync/v1/vault` for one immutable, public 16-byte salt and an encrypted passphrase check per account. `POST /sync/v1/entries` takes `{id, item_id, iv, ciphertext}` with canonical random UUIDs, a 12-byte base64 IV, and at most 65,536 decoded ciphertext bytes. Reusing an entry ID with identical bytes returns its original sequence; different bytes return 409. `GET /sync/v1/entries?after=&limit=` returns only the signed-in account's append-only entries and the latest cursor, with a maximum page of 100. Browser Web Crypto derives a nonextractable AES-256-GCM key from a separate vault passphrase and public salt using PBKDF2-HMAC-SHA256; each entry uses a fresh IV and authenticates the user, item, and entry IDs as additional data. The browser queues encrypted entries in IndexedDB when offline. No plaintext note, passphrase, or content key is sent to the service. The journal is text-only and not connected to device conversations.

For the loopback development bridge (#75), `STELLIS_DEVICE_ORIGIN` may name one exact loopback origin with a port. Credentialed CORS allows that origin to call `/sync/v1`; it is disabled by default. A foreign Origin fails preflight or mutating requests. The caller must use `credentials: 'include'` after a login on the account origin. This validates the browser connection only; a production cross-site identity flow cannot rely on these development cookies.

Planned encrypted media chunks and full conversation operation sync will accept opaque ciphertext envelopes only. Production authentication is expected to use OIDC session/device membership (#16). Hosted sync must never implement device-service audio or transcript endpoints. Browser key enrollment/decryption stays client-side (#17).
