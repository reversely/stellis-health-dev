# Working on the GN100

Stellis development happens on the GN100, an aarch64 Linux machine on the owner's Tailscale network (node `gn100-767e`). It holds the development checkout, the live Stellis service and its data. The Mac is a client: it opens SSH sessions and browser tunnels, and its disk is small. This page is for people and remote agents working on the GN100 over SSH. Values were checked on 2026-10-20.

## Connect

From the Mac:

```sh
ssh gn100-767e.local
```

- The host entry comes from NVIDIA Sync. `~/.ssh/config` includes `~/Library/Application Support/NVIDIA/Sync/config/ssh_config`, which sets user `springbuilt` and a `ProxyCommand` through NVIDIA Sync's Tailscale proxy (`--ts-hostname gn100-767e`). NVIDIA Sync must be installed on the Mac for this to connect.
- Agents run commands with `ssh -o BatchMode=yes gn100-767e.local '<command>'` so a missing key fails at once instead of waiting for a password.

### Rules for remote commands

- **Reuse an established SSH session.** Do not reconnect or restart Tailscale during ordinary development. A refused request is not evidence that Tailscale needs restarting. Inspect the current session and service first. For repeated commands and file transfers, reuse the session; a base64-encoded script sent through that session avoids opening extra SSH/SCP connections.

- **Use full paths for user tools.** A non-interactive SSH shell does not add `~/.local/bin` to `PATH`. Call `~/.local/bin/uv`, `~/.local/bin/nemoclaw` and `~/.local/bin/openshell` by path. `node`, `npm` and `gh` are in `/usr/bin`.
- **Send scripts as files.** Quotes inside a script inlined into `ssh '...'` get stripped or mangled, and a half-applied edit is the result. Write the script on the Mac, copy it with `scp script.py gn100-767e.local:/tmp/<dir>/`, then run `ssh gn100-767e.local 'python3 /tmp/<dir>/script.py'`. The same goes for PR bodies: copy the file and use `gh pr create --body-file`.
- **Guard `pkill -f` patterns.** `pkill -f "stellis --port 8811"` also matches the SSH shell running it and kills the session. Use a bracket so the pattern does not match itself: `pkill -f "[s]tellis --port 8811"`.
- **Ask before reading secrets.** The repo's `.env` and `~/.config/stellis/mcp.env` hold credentials. Ask the owner before reading or copying either.

## Layout

| Path | What it is |
| --- | --- |
| `~/Repos/stellis-dev` | Main checkout, on `main` |
| `~/Repos/stellis-dev/.agents/worktrees/runtime` | Worktree on branch `gn100-runtime`; the live service runs this code |
| `~/Repos/stellis-dev/.agents/worktrees/<name>` | Working worktrees, one per task |
| `~/stellis-data` | Live service data. Never point a test server at it |
| `~/stellis-runtime` | Python environment with the `stellis` command the service starts |
| `~/stellis-models` | Live speech and voice models |
| `~/.config/systemd/user/stellis.service` | User service unit, with drop-ins `agent.conf`, `mcp.conf`, `runtime.conf` and `voice.conf` in `stellis.service.d/` |
| `~/.cache/ms-playwright/chromium_headless_shell-1243/chrome-headless-shell-linux-arm64/` | Headless Chromium for browser checks |

## The live service

- `stellis.service` is an enabled systemd user service that serves `~/stellis-data` on `127.0.0.1:8765`, loopback only.
- The `runtime.conf` drop-in sets `WorkingDirectory` and `PYTHONPATH` to the runtime worktree, so the service runs whatever that worktree has checked out. On 2026-10-20 that was `1675d85`, behind `main`.
- Status and logs: `systemctl --user status stellis.service` and `journalctl --user -u stellis.service -n 100`.
- Deploying means updating the runtime worktree and running `systemctl --user restart stellis.service`. Ask the owner before deploying.
- To open the live app in a browser on the Mac, run `ssh -fN -L 8765:127.0.0.1:8765 gn100-767e.local`, then open `http://127.0.0.1:8765`.

## Develop a ticket

1. **Sync first.** Fetch and start from the current `main`:
   ```sh
   cd ~/Repos/stellis-dev && git fetch origin
   git worktree add .agents/worktrees/<name> -b <branch> origin/main
   ```
2. **Install JavaScript packages** in the new worktree with `npm ci`. The main checkout's `node_modules` is older than the lock file and lacks `@lexical/table`, so do not link to it.
3. **Run the tests** from the worktree:
   ```sh
   node --test tests/*.cjs
   ~/.local/bin/uv run --locked --with pytest python -m pytest -q tests
   ```
   Use `python -m pytest`, not `pytest`: `tests/test_live_asr_installer.py` imports `scripts`, which only resolves when the repo root is on the import path.
4. **Use an isolated test server** for browser checks. Give it its own data directory, and link the models instead of copying them:
   ```sh
   mkdir -p /tmp/<dir>/data && ln -sfn ~/stellis-data/models /tmp/<dir>/data/models
   STELLIS_DATA_DIR=/tmp/<dir>/data STELLIS_AUTH_MODE=open ~/.local/bin/uv run --locked stellis --port <port>
   ```
   - Check that the port is free with `ss -ltn` first. Other projects use ports here too: on 2026-10-20 a preview dashboard held 8799.
   - Do not save a Nebius or Tavily key in a test server. On the owner account, saving a key reconfigures the managed NemoClaw providers that the live service uses.
5. **Check the browser.** Either run Playwright on the GN100 (`~/.local/bin/uv run --with playwright python <script>`, with `executable_path` set to the headless Chromium above), or tunnel the test port to the Mac (`ssh -fN -L <port>:127.0.0.1:<port> gn100-767e.local`) and run the `layout-audit` skill there against `http://127.0.0.1:<port>`.
6. **Land one ticket at a time.** Rebase onto the current `main`, run both suites on the result, and push one commit per ticket from the GN100. `gh` there is signed in as `reversely`. Do not stack branches on unmerged work. Remove the worktree when the ticket is merged.
7. **Stop what you started.** Stop test servers and close tunnels when done.

## Separate local deployment

The authorized local-mode service is `stellis-local.service`, using the `local-runtime` worktree, port 8821 and `~/stellis-local-data`. It uses sandbox `stellis-local`, gateway 8990 and GN100 Ollama. The original service on 8765 and its gateway remain separate.

`deploy/profiles/local.env.example` includes explicit speech paths. New accounts must reuse the installed host assets; changing the workspace data directory must not make live speech disappear. Configure an existing service environment file without copying models or printing unrelated settings:

```sh
python3 scripts/configure_local_speech.py \
  --env-file ~/.config/stellis/local-runtime.env \
  --worker ~/.local/bin/stellis-audio-worker \
  --online ~/stellis-models/live-asr/sherpa-onnx-nemo-parakeet-unified-en-0.6b-int8-streaming-560ms \
  --parakeet ~/stellis-models/live-asr/sherpa-onnx-nemo-parakeet-tdt-0.6b-v2-int8 \
  --models ~/stellis-data/models
systemctl --user restart stellis-local.service
```

The command validates file presence before changing the environment file, preserves unrelated entries and writes it atomically with owner-only permissions. It does not download models, install software, change Tailscale or restart the original service. The model files under the original data root are reused read-only; account recordings remain isolated. Onboarding and Settings distinguish installed speech assets from a successful managed-agent connection check. `docs/evidence/421` records actual live speech and agent verification.
