# Stellis UI style guide

Use this guide for new screens and when revising existing controls. It records the accepted interface decisions; the [contrast workspace experiment](contrast-workspace-experiment.md) keeps the reference observations and revision history. Inspect any new user supplied reference before changing the related screen, and record what the reference shows separately from design inference.

## Visual foundation

| Role | Color | Use |
| --- | --- | --- |
| Dark core | `#27222B` | Home rail edge, recording rail, auth backdrop |
| Light paper | `#F7F5F6` | Default writing canvas and light card surfaces |
| White | `#FFFFFF` | Inputs and the light theme auth card |
| Dark ink | `#2A252F` | Text on paper |
| Muted mauve | `#413A48` | Dark primary controls and the home rail highlight |
| Dark control | `#37303D` | Secondary controls on the rail |
| Teal | `#335C63` | Home rail focal color, waveform, and light theme focus |
| Wine | `#654654` | Recording Stop action |

Use the roles already defined in `src/stellis/static/theme.css` before adding a color. Check text and icon contrast in both themes. The dark core has a red undertone and is never pure black. Keep the light document surface flat. Dark mode uses a flat mauve document surface.

The **desktop home left rail** is a WebGL fill (`static/rail-shader.js`) of five soft blobs in the user's palette `#495575`, `#56465C`, `#594F4F`, `#547980`, and `#45ADA8` over the dark core. The bright teal blob is smaller than the others. The blobs drift slowly, travel about a quarter of the rail, and lean only slightly toward the pointer. `--rail-blur` on `#rail-shader` sets edge softness from 0 to 1; the default is 0.55 so neighbouring colours blend. Static grain sits in the shader and in an SVG overlay at 30% opacity with an overlay blend. Reduced-motion preferences get one still frame. Without WebGL the rail falls back to the centered radial gradient. Its transparent header is continuous with the rail, with no separate top bar or divider. The recording rail, buttons, cards, notebook, and auth screen use solid fills. Do not spread the gradient across controls or other pages.

## Type and shape

- Use the existing Piazzolla display face for the brand and major page headings; use Inter for controls, labels, and body text. Keep a clear size and weight difference between page title, section title, and supporting text.
- Do not place an eyebrow or overline above a heading. Avoid decorative taglines and explanations that do not help someone act.
- The conversation document is square and attaches cleanly to its notebook tabs. Primary tabs (Notes, Transcript, and the recording page tabs) have a 7px top radius and square bottom corners; the large outward curves are retired. An unselected tab is a quiet raised surface with muted text and a hairline border. The selected tab is inverted (text-colour fill, surface-colour label) and sits on the 2px rule that joins it to the document. `.view-tabs` is the same shape for notebook view tabs. Keep My Notes and Enhanced Notes quieter than the primary tabs.
- **List widgets** (`.list-widget`) are a heading row (`.list-widget-head`) over plain rows (`.list-widget-rows`, `.list-widget-row`) on the page surface. There is no white card box and no fill. A hairline separates one row from the next and appears nowhere else.
- **Dates in lists are plain text, never pills.** Pills are for tags and categories. `formatListDate(isoDate)` in `shared/list-date.js` returns Today, Tomorrow, a weekday within the next six days, or a short date such as "Oct 24" (with the year when it is not the current one). Put the result in a `.list-widget-date` element at the right of the row. The Date format setting in Account settings (Relative, Short date, ISO) is stored per browser in localStorage under `stellis-date-format`, and the formatter reads it.
- Use small corners for cards and controls: roughly 6px for cards and 8px for ordinary inputs and buttons. Do not apply a large radius to every surface.

## Controls and states

- Style every interactive element explicitly. A primary button has a filled surface, clear text, at least a 44px touch target, and a visible hover, keyboard focus, and disabled state. The auth submit button is 48px tall. A secondary button is visibly quieter but still reads as a control. Never leave a browser default button in a finished screen.
- An **inverted** control fills with the theme's text colour and draws its glyph in the colour of the surface behind it, in both themes; it is not a flat accent fill. Summary regenerate is a 44px inverted icon button with no text button beside it.
- The theme switch is a bare 44px sun or moon icon in the header with no border, fill, or text. Take new UI icons from Tabler Icons (MIT, outline, 2px stroke) and record each in `static/icons.NOTICES.txt`.
- Keep Record, Import, Pause, and Stop visually related within the solid recording rail. Use the wine fill for Stop. Do not give Record a competing bright accent.
- Label inputs directly. Use a semantic `button` with an explicit type when it sits in a form. Icon-only buttons need an accessible name. Errors appear close to the action and describe what the user can do next.
- Show live recording and transcription where the user is working; make interruption and recovery states explicit. Match the status text to the actual recording state.
- **No Nebius key:** read `ai.configured` from `/api/v1/capabilities`. When it is false, hide the controls that need a key (Summary refresh and its menu item, Clean transcript, the question form, the recording AI Chat panel and toggle) and show one sentence with a link: "Summaries and questions need a Nebius API key. Add a key in Account settings". The categories status reads "Automatic categories need a Nebius API key." with the same link. The link is accent coloured, bold, underlined, and goes to Settings with the key field focused. Saved summaries stay editable, and saved answers and clean versions still display.
- Use short, familiar UI labels. Do not use interpuncts or middle dots (`·`) anywhere in user-facing copy, including metadata. Never mention Otter in the product UI. Show an unnamed speaker as `Speaker N` with no appended prompt.

## Screen hierarchy

- **Home:** The left rail is the file structure. At its head are the pinned entries **Meetings** (microphone; the Home list) and **To-dos** (check circle; opens `/todos`, the full To-dos page); there is no Chat entry because the app has no global chat. Under the **Library** title come collections (folder icon, count of notebooks), each expanding to its notebooks (colour dot, count of items) that expand to their meetings (microphone) and notes (file icon) newest first by capture or edit time; then a **Notebooks** group for notebooks without a collection, then **No notebook** (inbox icon). A chevron toggles every branch; collections and groups start open, notebooks start closed, and the choice is remembered per browser, while an active tag filter shows every match open. A notebook name opens its page; a collection name toggles it, since collections have no page yet. **New collection** (folder-plus) at the foot opens an inline name field; Enter creates, Escape cancels. Rows keep their full titles and the short date leading the first Summary topic. Notes have no page yet, so selecting one only reports that; they still drag and move; **Account settings** is pinned at its foot as a light glass button with a gear. Tag pills under the rail title filter the list: select several to show conversations carrying any of them, Untagged shows those with none, and Clear resets. Each rail row shows the full title, then the short date leading the first Summary topic. Titles, topics, meeting names, and progress points on Home wrap in full; they never end in an ellipsis. The main column starts with a heading row: **Home** with a ⋯ menu at its right (Edit widgets, Custom vocabulary, Tags, People, Recently deleted, each with an icon). **Edit widgets** opens a dialog that shows or hides each Home widget, kept per browser. Under it sits the action row: a rounded search field, the inverted **New note** button (note icon; it creates an untitled note and names it in the status line until notes get their own page) and the inverted **Record** button (microphone) joined to a chevron menu that holds **Import recording**. Below, at a main width of 720px or more, two columns sit side by side; narrower, they stack with the left column first. The left column is the **To-dos** widget. The right column holds, in order, **Coming up** when a calendar is connected, **Notebooks**, **Recent conversations**, and **Tags** with a + that opens the Tags dialog; every widget heading carries an icon. Notebooks are grouped under their collection (folder icon, the collection name), then notebooks outside any collection; a dashed **No notebook** strip follows and takes a dropped meeting or note out of its notebook. **Recent conversations** is a list widget of the ten newest meetings with a show-more button, the same tag pills as the sidebar (one shared selection), and a plain right-aligned date from `formatListDate`; its rows drag onto notebook and tag cards. Tag cards are neutral and compact, most used first: the tag name (which filters the rail to that tag), a count, and its five newest conversations; an empty tag invites a drag. Notebook colours belong to notebooks only. Coming up is a plain list of the next five meetings that have not ended, however far ahead, one row each with the day and time (Today, Tomorrow, a weekday within the week, then a short date), the full title, a notes button drawn as paper with a folded corner (lined once the meeting has notes), and a small ring-and-dot record button. A list and calendar toggle sits at the heading's right and is remembered per browser; the calendar shows Today, Tomorrow, and the third day as hour-grid columns with all-day events above, overlapping meetings side by side, and a bar with a dot at the current time in today's column. The notes button opens the meeting's notes in a dialog with Record and Done. A notebook card fills with its own palette colour and shows a notebook icon, the name, a + button, its newest item (meeting or note, each with its own icon), up to three progress points with check icons, and up to three older items; every item drags out to another card, a tag, or No notebook. Keep the cards visual and short: icons, colour, and space carry the structure rather than labels. At narrow widths the main column comes first and the sidebar follows on a solid dark band. A live recording keeps its card with a clear live state and current text when available. A sidebar meeting or note drags onto a notebook (a move) or onto No notebook (removal), a sidebar notebook drags onto a collection or onto the Notebooks group (out of its collection), and a meeting also drags onto a tag card to add that tag or onto a Home notebook card; a conversation has many tags and one notebook. The branch under the pointer takes a solid outline in the text colour, and a status line names the result. Every row has a **Move to…** button (arrows-move icon, shown on hover or focus on desktop and always on touch) that opens one dialog listing the destinations, so keyboard and touch users never need to drag. The conversation menu keeps Move to notebook.
- **To-dos:** One component (`static/todos-widget.js`) serves Home's left column, the pinned To-dos page at full width, and later a notebook page (scope: all notebooks, grouped under a notebook header, or one notebook, flat). A heading row carries the Open, Completed, and Canceled filters (icon buttons with small corners, the selected one inverted), then an input row that adds a to-do to the uncategorized note titled "To-dos" (created on first use; on a notebook, that notebook's own note), then plain rows with no card boxes. A row is a checkbox (toggles Open and Completed, and reopens a canceled item), the text, a thin grey source label that links to the meeting, and a right-aligned plain date: the due date for an open item, the completed date for Completed, the canceled date for Canceled. A pending agent suggestion shows as a quiet sparkles label on a faintly tinted row with a straight 2px left edge; the full suggestion UI is separate. The list runs to the end with no truncation; an empty filter shows one line.
- **Account settings and notebook pages:** Settings groups Profile, Sign-in, Custom vocabulary, Date format, Integrations, and Delete account, each under an icon tile. Primary actions are inverted buttons; Delete account uses the wine fill. A notebook page opens with a hero band in the notebook's colour and icon actions to add, edit, and delete.
- **Recording:** Keep capture actions and status in the dark rail; give the light notebook or transcript the wider reading area. Notes and Live transcript are the primary tabs.
- **Saved conversation:** Attach the primary file tabs to the square document. Keep transcript reading, seeking, notes, and related actions in predictable positions.
- **Authentication:** Use a centered paper card on the dark mauve backdrop. Make Sign in and Sign up clear, give the submit button the same deliberate shape and states as other primary actions, and support the light theme.

## Before merging a UI change

1. Inspect each named reference and relevant existing screen state. Recheck earlier feedback for the same workflow in [the reference ledger](otter-ui-reference.md) and [the contrast experiment](contrast-workspace-experiment.md).
2. Compare the rendered result in a browser at desktop and narrow widths, in both themes where available. Check the relevant default, hover, focus, disabled, loading, error, and alternate states. Check for horizontal overflow and page errors.
3. Verify behavior as well as appearance: tab changes, live updates, status transitions, and form submission where touched. Record observed results separately from inference and update this guide if an accepted design decision changes.
